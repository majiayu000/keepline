# Keepline 值得做的功能，以及何时应放弃

日期 2026-10-30。决定是**有条件继续验证**，不是立即开工清单。首批客群暂定为同一台 Mac 上、同时使用多个原生 Agent CLI 的个人开发者；多机器用户单独验证。

| 内容 | 依据 | 可信边界 |
|---|---|---|
| 问题存在 | [原始用户反馈与产品对照](01-competitor-research.md) | 原始用户反馈，不能推算需求规模 |
| 可以从已有基础延伸 | 固定版本 Keepline 源码 | 固定源码，未验安装版 |
| 谁先做、做了是否留存 | 以下产品建议 | 本轮判断，需真实使用验证 |

公开个别反馈说明问题存在；功能优先级仍需真实使用验证。

## 1. 先把基础体验当作门槛

多 Agent 工作台首先不能漏掉等待输入、把后台工作误报完成、把输入送错会话，或因界面更新丢掉运行中的任务。它还应保持打字、中文输入、复制和滚动可靠。

这是在做已有产品的质量，不应包装成又一个新功能。公开反馈包含 [状态误报](https://github.com/manaflow-ai/cmux/issues/1027)、[等输入不显眼](https://github.com/ParadevAI/Paradev/issues/8355)、[后台退出](https://github.com/stablyai/orca/issues/36262)与[输入停顿](https://github.com/ParadevAI/Paradev/issues/8108)。【用户原始反馈】

“需要你”入口沿用现有鸟瞰/侧栏，只补等待原因、等待时长和一次点击返回；通知保留聚焦静音、按会话静音。不用新增四个看板或固定状态解释规则引擎。

## 2. 三个优先验证的方向

### 第一项，任务结果核对页

用户问题是“它说做完了，我到底该看什么、还差什么”。[多 PR 就绪请求](https://github.com/ParadevAI/Paradev/issues/8410)和[评论草稿丢失](https://github.com/stablyai/orca/issues/36286)说明检查与反馈本身也是工作。【用户原始反馈】

最小体验沿用现有待办详情/“看进度”，补三类可追溯信息：

- 这项任务有哪些文件变动，点开 diff。
- 哪条命令或测试在什么目录、什么时间执行；PR 检查对应哪个 commit，是否已过期。
- 哪些问题还需用户核对；写下反馈后回到原 Agent，切换视图不丢未发送草稿。

第一步不必做完整编辑器或自动判定代码正确；可以先把当前任务、diff 和外部 PR/check 的正确入口连起来。一次会话可能混有用户或其他 Agent 的改动，不能把整个目录 diff 都归功于某个 Agent。CI 全绿、可合并和用户接受分别呈现。

这是对已有验收字段的深化，**建议作为最先验证的新增工作流**。【建议，待验证】 观察是否减少核对时间与遗漏，而不是统计卡片点击量。

### 第二项，独立任务环境的创建、准备与收尾

用户问题是“多开之后目录、依赖、端口和服务都乱了”。[环境与端口评论](https://news.ycombinator.com/item?id=48237005)、[独立基础设施评论](https://news.ycombinator.com/item?id=48244816)与[测试栈评论](https://news.ycombinator.com/item?id=48253274)重复提出这个问题；[已有脚本的用户](https://news.ycombinator.com/item?id=48247259)提供了替代方案。【用户原始反馈】

最小体验是在从待办开始时，可选独立 worktree，沿用项目已有的准备/运行脚本，展示该任务的目录、分支、实际服务端口与预览入口。结束时列清工作树是否还有未提交改动、服务是否仍运行，由用户选择保留或收尾。

不默认复制 `.env`、密钥或停止别的进程；有敏感配置需求时展示缺项并沿用明确授权。先接现有脚本，不开发容器编排平台或新的配置语言。多任务文件互不覆盖仍不意味着系统安全隔离，见 [Conductor 的明确边界](https://www.conductor.build/docs/concepts/git-worktrees)。

建议排第二，**这是更明确的一项新增能力**。【建议，待验证】 如果首批用户基本不并行修改同一仓库，或已有 workmux 脚本足够且不愿迁移，就降低优先级。

### 第三项，接手摘要与历史定位

用户问题是“昨天开了这些任务，今天不知道哪个该继续、为什么这么改”。[按任务保留工作现场](https://news.ycombinator.com/item?id=48242262)、[保存一组工作区](https://github.com/manaflow-ai/cmux/issues/2086)和[长对话目录](https://github.com/manaflow-ai/cmux/issues/11953)提供了不同角度的信号。【用户原始反馈】

沿用已有摘要，增加用户提示时间线和项目内跨会话搜索。结果标出任务、Agent、目录、日期，并能定位原始记录；点继续时清楚区分接回存活终端与启动新进程 resume。原始记录不在终端回看缓冲区时，也不假装能滚到不存在的画面。

第一步做本地文本与已有结构化记录检索，不强制新增模型摘要、向量库或跨模型记忆同步。【建议，待验证】 如果用户总是记得原会话、很少回看历史，就不扩展成知识管理系统。

## 3. 第二批候选，各自需要额外证据

| 方向 | 用户得到什么 | 证据与限制 | 当前建议 |
|---|---|---|---|
| 精确的 CLI / MCP 会话操作 | 让一个 Agent 把当前 diff 交给另一个审查，收回结果，少复制粘贴 | [Herdr 的 run/send](https://herdr.dev/)和 [Agent Deck](https://github.com/asheshgoplani/agent-deck)证明供给；本轮尚无独立样本量证明日常频率 | 待验证。先选一种入口、覆盖 list/read/send/wait 的真实需要，不同时造两套 API |
| 排队追加与中途纠偏 | 想到下一件事先排上，必要时立刻改方向，执行顺序可见 | [T3 当前 Queue/Steer 文档](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/composer.md)与[历史讨论](https://github.com/pingdotgg/t3code/discussions/6684) | 待验证。依照对应 Agent 已确认的原生能力，不猜回合结束，不另做万能注入器 |
| 网页预览与圈选反馈 | 看实际运行结果，指出哪个按钮或区域有问题 | [cmux 浏览器](https://cmux.com/)与 [Emdash](https://emdash.com/docs)证明供给；端口评论也有查看真实结果需求 | 待验证。先提供准确预览 URL 与截图反馈，再决定是否值得内嵌浏览器 |
| 上下文、额度与用量可见 | 发现快到限制、哪项任务上下文增长，避免盲目多开 | [Orca 单例](https://github.com/stablyai/orca/issues/36283)；Agent Deck 部分预算能力明确 untested | 待验证。不将 token 面额估算当账单；无官方数据则显示未知，不承诺硬预算拦截 |
| 跨设备 / 手机 | 在其他机器执行，离开电脑仍能查看或短回复 | [Herdr 多机日常使用](https://news.ycombinator.com/item?id=50300497)、[手机输入需求](https://news.ycombinator.com/item?id=50299174)，也有[为什么需要多机器的质疑](https://news.ycombinator.com/item?id=50300136) | 针对多机客群单独验证。若本人确实每天跨机器，可提前，不强推给所有用户 |
| 多仓库任务归组 | 一个交付同时检查前后端/共享库的变化 | [Orca 多仓库请求](https://github.com/stablyai/orca/issues/1099) | 单例待验证。先显示关联关系与外部入口，不先重建多根工作区模型 |
| 定时 / 事件触发的任务 | 把重复审查、问题分流交给 Agent | [Paradev 自动化](https://paradev.com/)和 [Emdash](https://emdash.com/docs)证明已有供给 | 暂缓。本轮没有足够独立需求说明首批用户愿意无人值守运行 |

## 4. 暂不作为投资重点

- 追逐 Agent 数量、主题、可自改整套 UI 或插件市场。它们在供给端已经很多，本轮不足以证明能改变日常使用。
- 为“做得通用”而同时做云平台、跨平台发布、自有模型路由与完整编辑器。范围大，且不是当前终端工作台最直接的接手价值。
- 默认自动批准、默认再开一个模型当总管、默认自动合并。公开反馈没有证明增加自治就能降低人的检查成本。

这些是本轮“暂不投入”的建议，不是宣称功能永远不需要。

## 5. 先让五个人用一次真实项目，再决定开发投入

以下是建议门槛，不是行业标准或已获得的数据。具体走查见 [协议](eval/user-observation-protocol.md)。

1. 找 5 位每天使用至少两个 Agent 会话的人，让他们先用现有工具完成一次结果核对、恢复接手或并行开工。保留至少一位 tmux 用户和一位单会话倾向者的反对意见。
2. 三个候选每次只验证一个，在一个真实项目中对照；任务难度相近，轮换工具顺序。已有版本做不到时用人工辅助原型，明确不能当运行验收。
3. 继续投入的建议门槛：5 人中至少 3 人两周内无需催促再次使用；同类任务的核对/准备时间中位数至少减少 30%，漏项不增加；基础输入与恢复没有新增严重问题。
4. 如果用户只需要通知与恢复、总关闭任务结果页，或纠正摘要的时间抵消收益，则先调整这两项已有能力，不继续堆系统。
5. 付费意愿另验。询问真实具体价格与持续使用理由，不能用点赞、star、“看起来不错”代替购买。

## 6. 风险与最终决定

单一模型平台可能通过原生 App 吸收通用管理功能，跨品牌工具也已覆盖差异化候选；[Qoder 的产品家族](https://qoder.com/)、[T3 Code](https://github.com/pingdotgg/t3code)与 [Conductor](https://www.conductor.build/docs)是可见供给。因此“多 Agent + 侧栏 + 恢复”不足以单独作为切换理由。【官方供给与本轮判断】

本轮建议保留用户原有订阅与 CLI，暂不增加模型转售依赖。上游格式、状态源、登录与额度规则仍会变化；没有证据可以承诺零适配成本。未进行价格或政策历史研究，不预测涨价。

采用方向：在可靠终端基础上验证结果核对、环境准备、接手历史。待验证：真实复用、误报、迁移成本和付费。暂不投入：完整平台化扩张。该决定在首批用户两周观察后重审。

已验：亲眼核对官方资料、用户原文和固定版本源码。没验：真实用户留存与所有竞品流程。相邻情况：tmux 用户可能完全不需要新 App；多机用户可能把远程排在最前，不能合成一个普适总分。
