Keepline 目标设计（新仓库用）

新仓库从头搭建时照这一份做：产品规则、模块边界、数据模型、写入协议、每个状态机的目标版本、并发、持久化、远程、故障和验收。它吸收了对旧实现的六层审计（41 个问题）和 2026-11-02 定下的全部决定，不依赖旧代码的行号。

0 · 这份设计支撑什么决定

支撑的决定：新仓库的骨架按这里搭，每个里程碑按第 13 节的验收条目判定完成。放弃条件：M1 的压测达不到指标，或 M3 前的审批指纹实验显示 id 不稳定，就回到对应章节改设计，不硬做下去。旧仓库 next/ 是参考实现：可以看它怎么接各家 Agent、怎么画界面，不照搬它的状态管理。

1 · 产品规则（不随实现变）

  • 做完了只由你定。一轮结束叫「等你验收」；Agent 说「完成了」只记下来，不改结局。看板四列，列名和状态同名（11-02 定）。
  • 宿主持有所有终端。关掉窗口、App 崩溃，终端和 Agent 照跑；只有宿主崩溃才会丢终端。
  • 任何 Agent 都能接。各家差异只在适配层（日志位置、Hook、画面规则、官方状态）；没有对话的程序可以用 OSC 7501 自报状态。
  • Agent 可信。本机同一用户的进程都可信，包括终端里的 Agent（11-02 定）；只防外来输入。
  • 手机只做聊天和审批，不做终端。自建中继，不用 Tailscale / iroh；中继只看到密文。
  • 派活回报。keepline run 在旁屏启动 Agent 交任务，每结束一轮把结果在你闲下来时打进你的输入框，注明不是用户说的话。
  • 不替用户改 Agent 的启动参数。例如不给 Codex 加 --no-daemon。
  • 仓库里不出现参考产品的名字。

会话状态：一个会话一个状态，所有界面同一个词、符号、颜色

没有「停下了」这个状态（11-02 定）。一轮自然结束就是「等你验收」；没结束就被打断才是「中断」，两者必须分开。中断的会话不会从界面上消失：它留在列表里，带上被打断的原因和「接着做」按钮（用原来的启动参数恢复对话）；不是你打断的，没看过之前算「要你注意」，看板放在「等你验收」列，不放进「做完了」。状态色只用来画会话；表单报错、额度、连接这类用另一套「好 / 注意 / 失败」色调，不借状态色。

2 · 进程与模块

一个二进制兼任宿主和命令行（keepline serve / keepline list …），一个桌面 App，一个中继，一个手机 App。App、CLI、手机都只是宿主的客户端，所有状态在宿主。

  1. Agent 跑在宿主开的 PTY 里，字节只经过终端层；终端层每个终端一个 Live，从不等全局状态。
  2. Agent 写的日志、调的 Hook 进观测层。
  3. 观测层只产出「信号」，投进状态线程的队列，自己不改状态。
  4. 状态线程把差异交给写库线程；回执要等写成功才发。
  5. 客户端的 Op 和订阅都走 control，按 client_id / request_id 去重。
  6. 手机经中继连 remote，每台手机一个设备记录、一个 token。

模块依赖规则：core 没有 I/O、不依赖任何别的模块，状态派生、Op 前提、回合规则都在这里，能单测；宿主和 App 都依赖 core；App 只经协议和宿主说话，不读宿主的库；手机只依赖 remote-proto 的 TypeScript 版本。

4 · 数据模型：七个聚合

旧实现是一整个 Workspace 加一个全局 revision，会话内容约每秒改一次，就把你的编辑全挡掉了。新模型按「谁改」拆开：观测层改的 Content 单独成流，和你的编辑互不干扰；每次改动有一个全局序号 seq，只用来排序和对账，不当锁用。

聚合包含谁改推送
Layoutspaces、tabs（分割树）你的布局 Op；Agent 的 split差异
TerminalsPTY 身份、ProcessState、启动参数、cwd宿主（spawn、退出、回收）差异
Sessions对话身份、绑定、结局、结局历史、挂的待办识别层（绑定）；你（结局）差异
Content每个会话的回合卡片：turn、waiting、approval、background、evidence只有观测层单独一条流，高频，不和你的编辑抢
Tasks待办、验收标准、证据拷贝、结局只有你差异
Settings按键存只有你差异
Health宿主健康、识别、远程、额度读数宿主差异

身份：对话身份是 (runtime, cli_session_id)，和 PTY、窗格都无关；终端身份和摆放位置分开，关窗格不等于终端结束（但会停掉它）。待办挂到会话：第一次绑定时用这个终端预设的待办，没有就用标签的默认待办，之后不再改。

一次请求的状态（App、CLI、手机共用）

在跑等待 / 过渡正常结束出错 / 中断中性由你决定双边框 = 终态

11-02 定：成功提示等确认再显示（本机通常几十毫秒）；超时显示「不确定是否成功」并给重试按钮。

会话状态派生：core::status::of，先命中先算

唯一的判定入口。输入是结局、回合、终端状态、Agent 是否活着、后台任务、更新时间；所有界面只做展示映射。「活着」= 是这个终端的当前对话、终端 Running、Agent 进程还在。

  1. 你定的结局：Completed / Abandoned（活着的 Agent 回合在跑时，先看回合）→做完了
  2. Deferred 且没到期→稍后再看
  3. 没在跑且超过 stale_days→很久没动
  4. turn = Waiting 且 Agent 活着（当前对话、终端 Running、进程还在）→等你回答
  5. turn = Waiting 但 Agent 不在了（原因：Agent 退出）→中断
  6. turn = Error，或终端 Failed / 非零退出→出错了
  7. turn = Running（活着，或日志 15 分钟内有更新），或 Completed 但子 Agent 还在→在跑
  8. turn = Completed，后台还有 shell / 监视 / 定时唤醒→等后台
  9. 活着的 Agent 还没开始第一轮→新开的
  10. turn = Completed→等你验收
  11. turn = Interrupted；或回合没结束但 Agent 不在了（日志里的 Running 过期、宿主重启）→中断
  12. 其余（记录不全，读不出这一轮怎么结束的）→中断（原因：不清楚）

6 · 宿主内部：一个状态线程 + 一个写库线程

旧实现一把全局锁下做 fsync、fork、跑 ps、写 socket，PTY 读的副作用也要等这把锁。新结构里状态线程只改内存，所有会阻塞的事都在别的线程。数据库用 WAL + synchronous=NORMAL：库不会坏，宿主崩溃时最多丢最后一次提交（11-02 定可以接受）；但回执在提交之后才发，所以你看到「成功」的一定已经落盘。

线程拥有可以阻塞吗
状态线程（1 个）全部聚合的内存状态不能：不做 I/O、不 fork、不等锁
写库线程（1 个）SQLite 连接可以：fsync 只卡它自己
每终端 pump这个终端的 Live（VT、PTY master、订阅者、写租约）只等自己的 PTY；画面信号投进状态线程的队列
副作用工人（池）spawn、ps / lsof、hooks.json、webhook、通知回执可以；结果作为信号投回
观测线程日志索引（自己的库）、FSEvents、Hook 接收可以；产出信号
每客户端读 / 写一条 socket写用 try_send，慢客户端被断开，不拖别人
监督者上面所有长期线程线程出错就重启，并记 Degraded 原因

8 · 宿主升级：两阶段交接

旧版新宿主收到 fd 就确认，旧宿主马上退出，之后新宿主任何一步失败都会挂断全部终端。新版先把会失败的步骤全做完再承诺；承诺之后旧宿主还多等一个 SERVING（11-02 定）。

9 · 信任模型

输入信任门控
本机同一用户的进程（App、CLI、终端里的 Agent）可信（11-02 定）runtime 目录 0700、socket 0600；不做额外确认

中继服务器不可信只见密文和每台手机的路由 token；握手前的连接 10s 超时，每个 token 限连接数
仓库内容（OSC 7 给出的目录）不可信跑 git 时关掉 fsmonitor 和外部 hook
拼进命令的文字（任务名、会话标题）不可信动作模板只做单引号转义，从不在双引号里展开
磁盘上的 Agent 日志、PTY 画面数据，不是指令不拼进命令；只用来派生状态

10 · 远程

手机能做的操作：会话列表、读会话、发消息、回答审批（带 id）、事件流。不再有原始按键（11-02 定）。每个请求带 request_id、10 秒超时；宿主按（设备, request_id）去重。关闭码拆开：4401 撤销（要重新配对）、4403 改了角色（重连即可）、4429 踢出（5 分钟冷却，11-02 定）。会话视图跟着对话走：终端里 /new 之后宿主推 session_switched。

11 · 持久化

表内容写入时机
ops每次改动的序号、聚合、差异写库线程按序号提交
layout · terminals · sessions · tasks · settings各聚合当前值同一事务
content回合卡片单独节流（最多每秒一次），丢了能从日志重建
requests（client_id, request_id）→ 结果，保留 24 小时和改动同一事务，保证「执行了」和「记住了」一致
notifications每会话一条回执：上次通知的 key通知前
devices每台手机：token hash、角色、冷却到期时间配对 / 改角色 / 踢出
日志索引（独立库）游标、检查点、隔离名单一批事件处理成功后

从旧仓库导入（一次性）

新宿主第一次启动时，如果找到旧库，只读打开，导入一次，之后不再碰它；旧库原样保留，导入失败可以删掉新库重来。

导入不导入
你做过的决定：待办、验收标准和挂上的证据、待办结局；每个会话的结局和结局历史、改过的会话名、挂的待办；空间（名字、目录）；设置 终端和标签布局（PTY 不能跨进程带过去，旧宿主在跑时请先用交接升级）；会话回合卡片（能从磁盘日志重建）；通知回执、设备配对（手机重新扫码，换成每台独立的 token）；日志索引（重建）

会话按 (runtime, cli_session_id) 对上，这个身份新旧一致；新仓库识别到同一段对话时，结局直接接上。

12 · 故障与恢复

故障用户看到系统做什么
写库失败（忙、磁盘满）状态栏小提示「后台没存上，重试中」内存照常，按序号重试；前台请求的回执要等写成功，所以你看到的是「结果未知」而不是假成功
Agent 在等你时被杀卡片变「中断」派生规则看存活，不靠事后清理
终端退出时写库失败仍然正确显示已退出退出事件进重试队列，不再只打日志
一个日志文件读不了识别正常，诊断里列出这个文件隔离名单，不拖住别的文件
长期线程出错状态栏小提示监督者重启；宿主不退出
宿主崩溃终端断开，重启后标 Interrupted，可用原参数恢复对话PTY 无法跨崩溃保留，这是唯一会丢终端的情况
交接任一步失败终端不断，App 提示升级没成功两阶段：SERVING 之前旧宿主都能接着服务

13 · 验收：每条规则怎么证明

要守住的规则怎么验收
无关的后台提交不挡你的编辑Agent 持续输出时连续标记完成 100 次，0 次被拒
每次操作要么生效要么明确失败，输入还在注入写库失败：表单不关、文字还在、按钮显示「结果未知 · 重试」
重发不执行两次回执前断开连接再重发同一 id，待办只多一个
布局操作互不冲掉Agent 执行 split 的同时改标签名、拖分隔线，三个改动都在
你确认停的终端就是实际停的确认框打开后 Agent 新分屏，关标签被拒并要求重新确认
批的就是你看到的那个审批两个问句相同、命令不同的审批先后出现，用旧卡片点允许被拒
需要你注意的状态有活着的 Agent 支撑Ctrl-C 掉正在问审批的 Agent，1 秒内卡片变「中断」，手机推送撤回
自然结束和被打断分得开一轮正常结束 → 等你验收；你按 Esc → 中断（你打断的，不提醒）；kill 掉 Agent → 中断（Agent 退出，要你注意）；三种都留在列表里
后台错误能被看见并自愈第一次写库返回 SQLITE_BUSY，状态栏出现提示，随后自动消失，数据正确
PTY 读不等状态20 个终端持续输出 + 日志批量写 + 每秒 50 个 Hook：PTY 读最大停顿 < 16ms（这就是旧仓库待压测的 I19，在新仓库里当验收指标）
终端会被回收开关 200 个终端后，fd 数和内存回到基线
交接不断终端在 Prepare / READY / COMMIT / SERVING 前后各注入一次失败，终端都不断
一台手机出事不影响别的撤销手机 A，A 的 token 无法让本机掉线；手机 B 照常
所有界面同一个状态固定一组会话快照，侧栏、看板、菜单栏、手机的状态逐个相等（单测）
