设计稿：先定设计，再改代码

这一页回答「问题清单里的问题，系统应该怎么设计才不会再出」。本页还没有任何代码改动。它要支撑的决定是：每一族选定一个目标设计（采用 / 否定 / 待验证），全部定下来之后才开始改。放弃条件：某一族的设计成本远高于修补，而它的问题都只是「推断」级，就先复现，复现不了就不做。

共 6 条设计原则、9 族设计、11 个需要你定的问题（紫色）。状态机现状见 架构页。

跨族的设计原则

41 个问题背后其实只有几条原则没守住。先定原则，各族的设计就是它们的展开。

P1每个请求都有自己的状态机
挂起 → 已确认 / 被拒（原因）/ 结果未知（超时）。界面以回执为准：成功提示等确认，失败时把输入还给你，结果未知时明说「不确定有没有生效」。

P2写入只带它在意的前提
不拿全局版本号当锁。新建不需要前提；改结局带「我看到的是 Open」；改对象带这个对象自己的版本。宿主上一次无关的提交不该挡住你。

P3派生状态只有一个来源，且要算上「观测源还活着吗」
「等你回答」「在跑」这类需要你注意的状态，必须有活着的进程或终端支撑；观测源没了就降级。所有界面调同一个函数，只做展示映射。

A · 编辑的前提与请求回执 问题 I1–I7

现状：9 种编辑查全局 revision：AddSpace、UpdateSpace、AddTask、UpdateTask、SetTaskOutcome、SetPendingTask、SetOutcome、AssignTask、SaveSessionTask。宿主每次提交（包括会话内容约每秒一次）都加 revision。客户端只有一个「忙」位，忙时非布局编辑直接丢；表单发出前就取走，失败不放回。

要守住的规则：

  • 一个编辑只会因为它要改的那个对象被别人改过而被拒
  • 你的每次操作要么生效，要么明确失败且输入还在；不存在静默消失
  • 成功提示只在宿主确认后出现
方案做法代价
A1 对象版本Task、Space、AgentSession 各带 rev；Update 类编辑带期望 rev模型和存储加字段；每处写入都要记得加 rev
A2 前提条件（推荐）每种编辑自带它在意的前提：Add 类不带；SetOutcome 带「我看到的结局」；UpdateTask 拆成字段级修改（改标题、改标准、挂证据）要逐个编辑设计前提；UpdateTask 要拆；但和 C 族用同一套机制
A3 过渡：拆计数器会话内容另起一个计数，不再加 Workspace revision改动最小，立刻消掉 I1 的大部分；但两个用户操作之间仍是粗锁

配套：客户端改成请求队列：每个请求一个 id 和状态（挂起 / 确认 / 被拒 / 未知），不再有丢弃；表单在确认后才关；乐观提示要么等确认，要么失败时撤回。宿主记住最近处理过的请求 id，重发同一个 id 直接返回上次结果（同时解决 I7 和手机的 I32）。

需要你定：

  • 成功提示等确认（本机 socket 通常几十毫秒，但碰上 fsync 会慢）还是乐观显示、失败撤回？
  • 结果未知（超时）时界面怎么说、给不给「重试」按钮？
  • A3 先做过渡，还是直接上 A2？

怎么验证设计对了：用例：Agent 持续输出时连续标记完成 100 次，0 次「工作台已变化」；忙时的每次点击都生效或明确报错；保存失败后表单内容还在。

决定：待定

B · 审批与按键的实例身份 问题 I8–I9

现状：审批的身份只是画面上那一行问句（如 "Do you want to proceed?"），回答时宿主只核对这一行还在。手机的「选 1/2/3」「Esc」直接写进终端，不核对画面。

要守住的规则：

  • 你批准的必须是你看到的那一个审批
  • 任何代替你按键的远程操作，都要指明它针对的是哪个画面
方案做法代价
B1 证据指纹（推荐）审批 id = 问句 + 证据行（命令、文件名）的指纹；卡片带上证据行给手机展示；回答带 id，宿主重读画面重算，不符就拒画面规则要能稳定截出证据行；重绘、折行可能让指纹抖动，需要规范化
B2 用 waiting_episode每次进入 Waiting 加 1，回答带 episode前提是连续两个审批之间一定经过 Running；这一点没核实，可能不成立
B3 按键也带画面身份没认出提问时手机不给数字按钮，只给「打开画面」；有提问时按键带它的 id手机少了一点「盲按」的灵活性

需要你定：

  • 手机还要不要保留不带校验的原始按键（选 1/2/3、Esc）？
  • 手机上审批必须展示命令全文吗（可能很长）？

怎么验证设计对了：构造两个问句相同、命令不同的审批先后出现，用旧卡片点允许 → 被拒；画面已经变了时按「选 1」→ 被拒。先核实 B2 的前提。

决定：待定

C · 布局编辑改成操作 问题 I10–I11

现状：PutTab 用客户端快照整块覆盖标签，并且豁免版本检查。改名、拖分隔线、移动窗格都走它，所以会冲掉并发的分屏。关标签时，确认框按本地快照列终端，宿主按当前状态停。

要守住的规则：

  • 一个布局操作只改它指名的那部分，并发的其他布局操作不丢
  • 你确认要停的终端，就是宿主实际停的终端
方案做法代价
C1 操作型编辑（推荐）RenameTab、ResizeSplit、MovePane、AddPane……宿主在当前布局上应用编辑种类变多；客户端的布局代码要从「改完整树再发」改成「发操作」
C2 每个标签一个版本PutTab 带期望版本，冲突时客户端基于新布局重做改动小；拖分隔线这种高频操作冲突后要重做
C3 宿主合并PutTab 时宿主把客户端不知道的窗格补回去规则难说清，容易出新的边界情况

配套：关标签：确认请求带上「我确认停这些终端」的列表，宿主发现多出来的就拒绝，让你重新确认。

需要你定：

  • 拖分隔线这种每秒几十次的操作，走 C1 还是 C2？

怎么验证设计对了：Agent 执行 keeplined split 的同时改标签名，两个改动都保留。

决定：待定

D · 不自愈的状态：观测源与宿主健康 问题 I12–I17

现状：「等你回答」不要求会话还活着；后台写库失败只打日志；补扫失败直接跳过、检查点照常前进；定时线程出错一次就永久退出。

要守住的规则：

  • 任何「需要你」的状态都必须有活着的观测源支撑，观测源没了就降级成「停了」或「中断」
  • 宿主内存和外显状态的偏差一定会被看见，并且会被重试修正
  • 检查点只在事件被成功处理之后前进
方案做法代价
派生规则Waiting 要求 Agent 还活着（session.current 且终端在跑）；否则落到「中断」。改在 core status::of 里（live() 和 recorded() 两条路径都要改）已定：显示「中断」
宿主健康状态机Healthy → Degraded（原因、重试中）→ Healthy。后台写失败进 Degraded，失败的写入（如 record_exit）进重试队列；App 显示一条提示要新增一个推给 App 的状态和一条提示
长期线程监督定时、订阅这类线程出错后由监督者重启，并进 Degraded；不让宿主退出（见 P5）要给每个长期线程定重启策略

需要你定：

  • Degraded 的提示放在哪里（状态栏？顶部条？）

怎么验证设计对了：故障注入：让 record_exit 第一次写库返回 SQLITE_BUSY，终端状态最终仍变成 Exited；Ctrl-C 掉等审批的 Agent，卡片 1 分钟内离开「等你回答」。

决定：已定（11-02）：Agent 在等审批时被杀，显示「中断」。

E · 锁与 I/O 分离、终端回收 问题 I18–I23

现状：一把全局 Host 锁下做 fsync（synchronous=FULL）、fork、/bin/ps、读对话记录、等日志库锁、交接时写 socket。PTY pump 的副作用也要拿这把锁。结束的终端从不移出内存。

要守住的规则：

  • 锁内只改内存、发通知，不做可能阻塞超过毫秒级的 I/O
  • 读 PTY 不依赖全局锁
  • 终端结束后，它的 fd 和缓冲会被释放
方案做法代价
E2 先降 fsync 级别WAL 下改成 synchronous=NORMAL：库不会坏，崩溃时最多丢最后一次提交一行改动；要接受崩溃丢最后一次编辑
E3 pump 不直接拿 Host 锁标题、命令完成这类副作用改成发消息给一个处理线程多一个队列；顺序要保证
E1 单写线程锁内生成新状态和差异，交给写线程落库失去「落库成功才换内存」，落库失败要走 D 的 Degraded；改动最大

需要你定：

  • 能否接受宿主崩溃时丢最后一次编辑（E2）？
  • 要先压测确认 I19 真的会卡（目前是推断）再动 E1/E3 吗？

怎么验证设计对了：压测：20 个终端持续输出 + 日志批量写入 + 频繁 Hook，测 PTY 读的最大停顿；改前改后对比。开关 200 个终端后，fd 数回到基线。

决定：待定

F · 交接两阶段提交 问题 I24

现状：新宿主收到 fd 就发 ACK，旧宿主收到即退出；之后的拿锁、开库、恢复 VT 任何一步失败，全部终端被挂断。

要守住的规则：

  • 旧宿主退出之前，新宿主已经完成所有会失败的步骤
方案做法代价
两阶段（推荐）PREPARE：新宿主收 fd、开库、恢复 VT，都成功才发 READY；COMMIT：旧宿主释放 host.lock 并退出，新宿主拿锁开始服务要处理「两个进程同时开着库」（WAL 允许，但写入要只有一方）；拿锁仍在 COMMIT 后，要保证旧宿主退出够快

需要你定：

  • COMMIT 后新宿主仍然失败（极少见）时，接受挂断，还是让旧宿主先不退出、多等一个确认？

怎么验证设计对了：在 PREPARE 的每一步注入失败，旧宿主都继续服务、终端不断。

决定：待定

G · 本机信任模型 问题 I25–I31

现状：同一用户的任何进程（包括终端里的 Agent）都有全部权限，能生成完全控制的配对链接；插件默认启用、直接执行命令；所有手机共用一个机器码；配对链接打开就保存。

要守住的规则：

  • 外来的配对链接、新设备第一次都要你确认
  • 撤销一台手机只影响这一台，别人顶替也只影响那一台
方案做法代价
每台手机独立路由 token撤销即失效；中继上的顶替只影响一台配对和中继注册流程要改
零散加固配对链接先确认再保存；握手前的会话 10s 超时；动作模板不在双引号里展开；不可信目录里的 git 关掉 fsmonitor各自都小

怎么验证设计对了：撤销手机 A 后，A 的凭据无法让本机掉线；从网页打开配对链接，不确认就不保存。

决定：已定（11-02）：本机同一用户的进程（包括终端里的 Agent）可信，I27、I31 不修。不可信的只有外来输入：网页打开的配对链接（I26）、中继和手机（I25、I30）、仓库内容（I29）、拼进命令的任务文字（I28）。这一族只做这些的加固，插件首次确认去掉。

H · 手机请求与订阅 问题 I32–I37

现状：请求没有超时、没有幂等 id；会话视图按终端取会话，换会话后不跟；4401 同时表示撤销、改角色、踢出；events 流结束后不重订；重连有竞态。

要守住的规则：

  • 手机的每个请求都会在有限时间内得到结果（成功 / 失败 / 未知）
  • 重发不会让同一件事做两次
  • 视图跟着会话走，不跟着终端走
方案做法代价
复用 A 的请求状态机超时 + 幂等 id，宿主按（设备，请求 id）去重宿主要存最近的请求结果
关闭码拆开4401 撤销（要重新配对）、改角色（重连即可）、踢出（冷却一段时间）各用一个码手机和宿主一起改
心跳 + 重订心跳检测半开连接；events 结束自动重订；会话切换推一条事件多一点流量

需要你定：

  • 踢出之后要不要冷却时间，比如 5 分钟内拒绝重连？

怎么验证设计对了：发送时断网再恢复，消息只出现一次；终端里 /new 之后，手机 5 秒内切到新会话。

决定：待定

I · 唯一的状态派生 问题 I38–I40

现状：已统一（c6da3508，11-02 21:48）：状态只在 core status::of 判定一次，侧栏、看板、菜单栏、手机都调它。问题清单的 I38 是读了统一前的代码。剩下的只有菜单栏另存一份 Workspace（I39，差一拍）和窗格重连（I40，与分组无关）。

要守住的规则：

  • 同一个会话，在任何界面上只有一个分组结果
方案做法代价
core 里一个 status 函数（推荐）输入：结局、回合、终端状态、活跃程度、后台 shell、是否看过；输出一个 Status。侧栏、看板、菜单栏、通知只做展示映射要先把分歧处的口径定下来；三处调用都要改

配套：菜单栏和工作台在同一进程里，共用一份 Workspace。

怎么验证设计对了：对一组固定的会话快照，侧栏、看板、菜单栏的分组结果完全一致（可做成单测）。

决定：已解决：分组已统一，原来三个口径问题由 status::of 回答（活着出错 → 出错了；只剩后台 shell → 等后台）。只剩 D 族「被杀 → 中断」要改进这同一个函数。
