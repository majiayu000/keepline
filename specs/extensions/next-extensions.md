## 1. 同文件并行改动预警

**要支撑的决定**：同一工作区里多个 Agent 并行改代码时，是否需要 Keepline 主动拦一下，还是继续靠人记得开 worktree。

**现在已有**：`keeplined/src/content.rs` 在 Edit / Write / apply_patch 成功（exit 0）时已从 `file_path` / `path` / patch 文本里取出改动路径，带时间和来源偏移写进证据。缺的是跨会话按「工作区 + 文件」聚合。

**做什么**
- 后台按 `(仓库根, 相对路径)` 维护最近 N 小时内改过它的会话集合。
- 同一文件被 ≥ 2 个仍活着的会话改过 → 两个会话的左栏行和窗格标题栏出一个「撞文件」标记，悬停列出文件和对方会话。
- 标记上给两个动作：跳到对方会话；「把这个会话挪到新 worktree」（新建 worktree 并在其中开同一 Agent 的恢复命令，原会话不动）。

**验收**
| 指标 | 门槛 | 怎么量 |
|---|---|---|
| 检出率 | 人为制造的 10 次撞文件全部标出 | 两个 Claude / Codex 会话分别改同一文件 |
| 误报 | 不同仓库同名文件、同一会话反复改同一文件，0 次误标 | 构造用例 |
| 延迟 | 第二次改动落盘后 ≤ 3 s 出标记 | 计时 |

**放弃条件**：两周日常使用中真实撞文件 < 2 次，说明你已经靠 worktree 习惯解决了，降级成「诊断页里的一个列表」，不进左栏。

## 1b. 侧栏 / 通知里直接回答审批

2026-10-31 用户决定从产品卡「首版不做」提前，接在第 1 项之后。依据：cmux、omux、tuios、agent-hud-open、Open Island 都能在列表或通知里答审批；官方 Agent View 只能回编号选项，权限对话框要进到会话里答（调研：`~/peerscope/keepline/rounds/20261030-s2/`）。

**要支撑的决定**：等你的审批是否值得在不切到画面的情况下直接回答，还是跳过去答就够了。

**现在已有**：审批框识别（`11d6ae6` 补过漏识别），左栏「等你」计数，通知点击直达画面。

**做什么**
- 左栏行和系统通知上显示审批的原文摘要（命令或文件），给「允许一次 / 拒绝 / 打开画面」三个动作；只把对应按键发给该画面的 PTY，不改 Agent 自己的权限或信任设置。
- 选项多于三个或识别不确定时，只给「打开画面」。

**验收**
| 指标 | 门槛 | 怎么量 |
|---|---|---|
| 答对 | Claude、Codex 各 10 次审批，从左栏答完后画面里的选择和点的一致 | 真实会话 |
| 不误发 | 审批框已被人在画面里答掉后再点，0 次把按键发进普通输入 | 构造用例 |

**放弃条件**：两周里从左栏答的次数少于跳进画面答的 1/4，降级为通知里只给「打开画面」。

## 2. 按会话认领 git 改动

**要支撑的决定**：「只提交这个会话的改动」是否值得做成一键操作，替代现在提交前人工挑文件和 hunk。

**现在已有**：同第 1 项的文件归属；`layout.rs` 已能从 `.git/HEAD` 读分支（含 linked worktree）。

**做什么**
- 会话卡片 / 窗格右键加「这个会话的改动」：列出它改过、且当前仍是未提交状态的文件，显示 diff。
- 「只暂存这些」：文件只被这一个会话改过 → 整个文件暂存；被多个会话改过 → 标为混改，不自动暂存，打开 diff 让人挑。
- 不做自动 commit，提交仍由人或 Agent 自己发起。

**验收**
| 指标 | 门槛 |
|---|---|
| 归属正确 | 3 个会话并行改 15 个文件，单独归属的文件 100% 正确；混改文件全部标为混改，不误暂存 |
| 已提交 / 已回退的文件 | 不再出现在列表里 |
| 用户改动 | 人手改过、没有任何会话证据的文件不归给任何会话 |

**放弃条件**：hunk 级归属做不准（Agent 改完人又改同一处）且文件级不够用 → 只保留「这个会话改过的文件列表」，不做暂存按钮。

## 3. 完成声明自动核对

**要支撑的决定**：「做完了」卡片能否直接告诉你「声称完成但没验证 / 验证失败」，减少你逐个点开核对的次数。

**现在已有**：`completed_claim`（自述完成）；证据里有命令、退出码、测试计数；插件系统里 rules 类型（哪些命令算跑过验证）在做，正要解决 bun、vitest 项目被误判为没跑验证。

**做什么**
- 回合结束且 `completed_claim` 为真时，按 rules 判断本回合有没有验证命令、最后一次结果是否成功、成功之后是否又改过文件。
- 卡片上给三种结论之一：**已验**（验证在最后一次改动之后且通过）、**没验**（没跑或跑在改动之前）、**验证失败**（声称完成但最后一次验证非 0）。
- 「做完了」分组内按 验证失败 > 没验 > 已验 排序。

**验收**
| 指标 | 门槛 | 怎么量 |
|---|---|---|
| 判断准确 | 从本机真实历史抽 50 个「自述完成」回合，人工标注后一致率 ≥ 90% | `examples/claim_scan.rs` 扩展出标注表 |
| 误判方向 | 「验证失败」不得误判成「已验」，0 次 | 同上 |

**放弃条件**：一致率达不到 80%，且主要原因是验证命令写法太杂、rules 盖不住 → 只显示「本回合最后一次命令的退出码」，不下结论。

## 4. 卡住 / 空转识别

**要支撑的决定**：是否给「在跑」再分出一个「可能卡住了」，让你不用挨个看正在跑的会话。

**现在已有**：回合状态、工具调用和退出码记录（`session_records`）、Inbox 状态集。

**做什么**：在跑的回合满足任一条件就标「可能卡住」：
- 同一命令或同一错误摘要在本回合内连续出现 ≥ 4 次；
- 回合已跑 ≥ 20 分钟，且最近 10 分钟没有任何文件改动、也没有新的成功命令；
- 同一文件被反复改了又回退（同一 patch 来回 ≥ 3 次）。
只提示，不打断，也不杀进程。

**验收**：回放 30 个真实长回合，人工标注卡住与否；精确率 ≥ 70%（宁可漏报，不刷屏），每个会话每回合最多提醒 1 次。

**放弃条件**：精确率 < 50% → 不进 Inbox，只在诊断页列出可疑回合。

## 5. 额度将尽时换 Agent 接力

**要支撑的决定**：Claude / Codex 某一家额度快用完时，是否值得让 Keepline 帮你把手上的会话交给另一家继续。

**现在已有**：额度和到期预测只在 `menubar-tauri/`；`next/` 里没有额度数据，也没有跨 Agent 的上下文打包。会话恢复只覆盖同一 Agent。

**做什么**
1. 先把额度读取移进 `keeplined`（读法与 menubar-tauri 一致），App 顶栏显示两家剩余与预计用完时间。
2. 预计 ≤ 30 分钟用完时，在仍在用这家额度的会话上提示。
3. 「换 Agent 接力」：生成交接包（用户原话、已完成的证据、未完成的项、当前未提交改动的文件列表），在同一目录开另一家 Agent，交接包作为第一条输入。

**验收**
| 指标 | 门槛 |
|---|---|
| 预测误差 | 「预计用完时间」与实际误差 ≤ 20%（取 10 次） |
| 接力可用 | 10 次真实接力中，新 Agent 不追问已完成的上下文、直接继续的 ≥ 7 次 |

**注意**：验收要花真实模型额度，必须先得到你的授权（当前决定默认不花额度）。

**放弃条件**：第 1 步完成后，若实际很少撞到额度上限（一个月 < 3 次），只保留顶栏额度显示，不做接力。

## 6. 任务排队派给空闲 Agent

**要支撑的决定**：Keepline 是否从「看 Agent」进一步变成「给 Agent 派活」，尤其是无人值守时段。

**现在已有**：待办面板（tasks）、启动和恢复会话；第 4 项完成后才能更可靠地判断「真的空闲」。

**做什么**：待办可标「可派发」，并写好目标目录、Agent 种类、第一句话；有空闲槽位（同时运行数 ≤ 你设的上限）时自动开新会话执行；跑完按第 3 项的结论归入「做完了」。不自动 commit、不自动 push。

**验收**：连续 2 小时排 5 个任务，全部按顺序开起来，不超并发上限，结束后 Keepline 自身 CPU 不超过浸泡测试门槛；任一任务出错不影响后面的任务。

**放弃条件**：你实际不在无人值守时段跑 Agent，或更习惯用 Agent 自带的队列 / 定时功能 → 不做。

## 7. 手机处理等你的会话

**要支撑的决定**：离开电脑时，是否需要在手机上回应「等你回答」，避免 Agent 白等。

**现在已有**：Inbox 的 Waiting 状态；系统通知（M4）还没完成，真实通知展示待你授权。

**做什么**：先只做推送（复用 M4 通知出口，加一个手机推送渠道，如 ntfy / Bark），内容是会话名和最后一个问题；第二步才考虑在手机上回复，回复需要本机开一个仅限局域网或经隧道、带一次性令牌的入口。

**验收**：推送 ≤ 10 s 到达；回复路径默认关闭，打开时必须有令牌和过期时间。

**放弃条件**：M4 没完成前不开工；只要推送就够用，就不做回复（回复牵涉远程输入终端，安全成本高）。
