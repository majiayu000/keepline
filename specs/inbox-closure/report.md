# 收件箱、结局状态与「你在这里」卡：实现与卡片准确性报告

日期：2026-10-20。分支：`claude/inbox-closure-0fb864`（基于 `main@0d32d2b`）。

## 结论

- **决定：采用「只靠机械证据生成卡片」，不触发产品卡第 8 节第二条放弃条件；整体状态为「待验证（倾向采用）」**，最终以作者连续一周自用（第 8 节第三条）为准。
- 第一版卡片确实“经常不准”：25 个真实会话中，「做成了」只有 44% 准确，「停在」44% 可用，「下一步」24% 可用。如果停在第一版，就应触发放弃条件。
- 错误几乎都来自几条可修的提取规则，数据来源本身没有问题。最主要的一类是把命令**输出里提到**的测试数、PR 链接、提交行，当成本会话**自己做成**的事。修复后，在 20 个新抽的会话上，四个字段的准确率为 90%–95%（见第 4 节）。
- 剩下的误差有三类：同一检查改了参数重跑后，旧的失败没有被覆盖；自动化任务的回复是一整段 JSON；用户粘贴的大段内容被当成原话。另外 59% 的会话「做成了」为「无」，问答、调研类会话本来就没有机械证据，这时用户仍要读最后回复，所以卡片在「停在」里直接引用了最后回复。
- 分组上的发现：**只靠机械证据分不出「真做完」和「做一半」**。回合正常结束后，会话一律进入「待核对」，靠用户读卡片来判断。原来按“完成”等关键词分组，在样本里明显出错（例如“做成了，现在有两份文档”被分进「做一半停了」），所以改成以运行时自己的回合结束记录为准（见 2.2 偏差）。

## 2. 实现说明

### 2.1 后端

- **迁移 020 `session_outcomes`**（`src/infrastructure/database/migrations/020_session_outcomes.ts`）：结局按 `runtime_id + runtime_session_id` 记录，字段包括结局（`snoozed` / `abandoned`）、原因、再看时间、设置时的最后回合 `turn_id`、设置时的活动时间、设置时间和撤销时间。数据库 CHECK 约束要求暂存必须带原因和再看时间。撤销只写 `revoked_at`，不删除记录，历史保留。
- **已完成**复用账本验收：写入当前回合的 `ledger_acceptances`。有未完成的确认清单时，记为 `accepted_with_gaps`，并列出被放弃的条目。没有回合记录的会话不能标记完成，返回 400，但可以放弃。
- **重新打开**：会话出现新回合后（`turn_id` 变化；没有回合标识时看活动时间是否更晚），原结局不再生效，并以 `reopenedFrom` 字段保留供界面显示。设置任何结局之前，会先清掉当前回合已有的结局，所以撤销后一定回到未闭环。
- **结局与进程互不推导**：写结局不碰进程；进程退出也不会产生结局（有测试覆盖）。
- **服务与路由**：`src/services/inbox.service.ts` 和 `src/web/api/routes/inbox.ts`，同时挂在 Web `/api/inbox` 和 local-api `/api/v1/inbox`，meta 新增 `inbox.outcomes` 能力。
  - `GET /` 返回分组后的快照，`?staleDays=` 可临时覆盖天数。
  - `GET /:sessionId` 返回单行。
  - `PUT /:sessionId/outcome` 写结局；`DELETE /:sessionId/outcome` 撤销。
- **“很久没动”天数可配置**：新增 `ledger.inboxStaleDays`，默认 3，通过现有 `PUT /api/settings/ledger` 修改。

### 2.2 分组推导

纯函数 `deriveInboxGroup`（`src/domain/inbox/grouping.ts`），读取时推导，不落库。判断顺序：

1. 已完成或已放弃 → 已结束。暂存且未到期 → 暂存。暂存已到期 → 回到未闭环并标“到期”，“很久没动”从到期时间起算。
2. 不在运行回合，且超过 N 天没有新回合 → 很久没动（同时保留“原本在”的分组）。
3. 其余按顺序归入第一个匹配的分组：
   - 等你回答：有明确输入请求，且进程没有确认退出。
   - 出错了：以 API 或登录错误回复结束、额度受限、最后一轮没有结束就丢失进程，或未结束回合的最后一步非零退出。
   - 进行中：回合未结束，且进程在线或 15 分钟内有记录。
   - 待核对：回合已结束，回复没有反问用户。
   - 做一半停了：其余情况。

**与规范的偏差**（依据是第 4 节的真实数据；建议同步进 terminal-workbench product.md 第 5 节）：

| 规范原文 | 实现 | 原因 |
|---|---|---|
| 待核对 = “声称完成” | 回合有结束记录（Codex `task_complete`、Claude 最终回复）即算；回复以提问结尾则归入「做一半停了」 | 关键词判断在样本里误分明显；回合结束是运行时自己的信号，是否真完成交给用户读卡片 |
| 出错了包含“会话为 lost” | 只有最后一轮**没有结束**时，lost 才算出错 | 扫描器把回复结束后关掉的终端也记成 lost；样本 A 的 5 个 lost 会话里有 4 个最后一轮有结束记录（3 个是 API 错误回复，已改由 API 错误规则归入「出错了」；1 个正常完成） |
| （未定义） | 进行中要求进程在线，或 15 分钟内有记录 | 进程状态未知时，几天前未结束的回合不能一直算“进行中” |

单元测试覆盖 A15 的全部情形（`src/__tests__/inbox/grouping.test.ts`、`api.test.ts`）：等待输入、出错、声称完成、空闲未完成、超期各一个；分别标记完成、暂存、放弃；一个暂存到期、一个已完成会话出现新回合；结局不停进程；进程退出不产生结局；天数可配置；可撤销。

### 2.3 「你在这里」卡

纯函数 `buildHereCard`（`src/domain/inbox/card.ts`），所有字段都由规则生成，没有模型参与：

| 字段 | 规则 |
|---|---|
| 你要它 | 用户原话，含追加和追问。去掉压缩摘要、`<command-…>` 等系统文本；有真实请求时去掉单独的寒暄；Codex 附件头只保留 “My request” 之后的内容。没有内容时显示「无」 |
| 做成了 | 只认机械证据，规则见下方。没有时显示「无」 |
| 停在 | 有明确输入请求时显示问题。回合已结束时引用最后回复（并附最后一步）。回合未结束时显示最后一步及结果（成功 / 失败 exit N / 尚未收到结果） |
| 下一步 | 由分组和前三项推导，界面标“推断”。不引用不存在的证据 |

「做成了」的具体规则：

- 检查：命令段的开头必须是检查命令（test、build、lint、typecheck 等）；heredoc 正文不算命令；只显示每条检查的最新结果，重定向路径不同的重跑合并为一条。
- PR 和提交：只有同一次调用里执行了 `gh pr create`/`merge` 或 `git commit` 才算。
- 文件：只认文件改动证据。

账本侧还做了两处小修，都属于已有行为的修正：

- `latestActivity` 跳过 update_plan、wrap_up、TodoWrite、ToolSearch 这类记账工具，并展开 Codex `exec` 脚本里的真实命令（`src/services/ledger/service.ts`，计算版本 36 → 37）。
- `extractAsks` 不再把“`npm i x` 这是什么”这种带中文说明的请求当作粘贴的命令丢掉（`src/domain/ledger/matcher.ts`）。

## 4. 卡片准确性抽查

### 4.1 方法

- `scripts/inbox-card-sample.ts` 使用隔离的 `KEEPLINE_HOME`（scratchpad 目录），只读本机 `~/.claude`、`~/.codex` 最近 30 天的记录，离线生成全部卡片：469 个根会话，其中 Codex 331 个、Claude Code 138 个。整个过程不写 Hook，不写默认的 `~/.keepline`。
- 另写了一个独立脚本，不复用 Keepline 的解析器，直接从原始 JSONL 提取摘要：首末几条用户消息、最后几次工具调用及结果、检查命令、改动文件、提交、最后回复。逐字段对照这份摘要核对卡片。
- 核对人是本会话（模型），不是作者本人。判定标准：
  - 你要它：显示的是用户对主要请求的原话。
  - 做成了：没有虚假条目（不是本会话做的，或是输出文本误识别），也没有把旧的失败当作当前状态。“无”只有在原始记录确实没有可提取的成果时才算准确。
  - 停在：说的是真实的最后状态；可用 = 不翻记录也能看懂停在哪。
  - 下一步：与事实一致，且能指导下一步动作。
- 样本按分组和运行时分层：
  - 样本 A：25 个，用于找错和定规则，第一版与修复后各评一次。
  - 样本 B：20 个新会话，与 A 不重叠，只用修复后的规则评一次，用来检查是否过拟合。

### 4.2 结果

| 字段 | A 第一版（25） | A 修复后（25，同一批） | **B 新样本（20，修复后）** |
|---|---|---|---|
| 你要它：准确 / 可用 | 22 / 22（88%） | 24 / 24（96%） | **18 / 18（90%）** |
| 做成了：准确 / 可用 | 11 / 11（44%） | 22 / 22（88%） | **19 / 19（95%）** |
| 停在：准确 / 可用 | 25（100%）/ 11（44%） | 25 / 24（96%） | **20（100%）/ 18（90%）** |
| 下一步：准确 / 可用 | 6 / 6（24%） | 24 / 24（96%） | **19 / 19（95%）** |

修复后合计 45 个会话：你要它 93%，做成了 91%，停在可用 93%，下一步 96%。

说明：

- “A 修复后”与修复规则用的是同一批样本，偏乐观；以 B 为准。
- B 评完之后又修了两处：Codex 附件头导致原话为空（B#20），heredoc 正文被当成命令（A#17，本会话自身）。表中数字没有计入这两处修复。
- 全量 469 个会话里，「做成了」为「无」的占 59%（279 个），「你要它」为空 7 个，「停在」为「无」2 个。

### 4.3 典型错误

第一版（已修复）：

1. **输出文本被当成证据**（影响最大）。读 README 或日志时输出里的 “3 passed”、`Tests:`，被当成测试通过；`gh pr list` 列出的 18 个 PR、别人仓库的 PR 链接、读设计稿时看到的 `[branch hash] msg`，被当成本会话的 PR 或提交；PR 正文里写的 “bun test 通过” 被当成检查。
2. **「停在」没有信息量**。Codex 用 `exec` 跑 JS 脚本，最后一步只显示“exec（成功）”；Claude 桌面会话的最后一步是 `wrap_up`、`update_plan`。
3. **把 lost 当成出错**。终端在正常回复后被关掉，也被归为「出错了」，下一步还写着“进程意外丢失”。
4. **按关键词判断完成**。回合正常结束但回复里没有“完成”二字的会话，被分进「做一半停了」。
5. **原话混入系统文本和寒暄**（如“你好”、上下文压缩摘要）；“npm i x 这是什么”这类请求被当成命令丢掉。
6. **同一检查改了重定向路径重跑**（`make build > a.log` 与 `> b.log`），旧的失败没有被覆盖。

修复后仍存在（B 中出现）：

1. 同一检查换了参数重跑（如 `go test -run X` 失败后用别的参数通过），旧失败仍显示，「下一步」会提示“最近一次检查失败”（B#7）。最后回复说“30 项回归通过”，卡片却显示失败。这种情况下卡片仍然**保守**：它不会替 Agent 宣称通过。
2. 自动化任务（Harness workflow）的最后回复是一整段 JSON，「停在」的摘录读不懂（B#14、B#16）。
3. 用户粘贴的大段网页或终端输出，被当作第一条原话（B#19、A#23）。界面同时显示首条和最近两条，影响有限。
4. 漏报：通过工具合并 PR、但输出里没有 PR 链接时，不计入「做成了」（A#10）。目前的取舍是宁缺勿错。

### 4.4 对照放弃条件

产品卡第 8 节第二条：“「你在这里」卡经常不准，用户仍需翻记录”。

- **不准**：修复后，新样本四个字段的准确率在 90%–95%，剩下的误差偏保守（漏报、旧失败），没有发现替 Agent 宣称完成的情况。**不构成“经常不准”。**
- **仍需翻记录**：调研、问答类会话（全量的 59%）没有机械成果，「做成了」为「无」。这时「停在」直接引用最后回复，大多不用翻原始记录。但要判断“做得对不对”，仍要读回复全文，这符合「待核对」的定义。
- **决定**：采用机械证据路线，不引入模型补写「做成了」。卡片与分组规则的修正写入本分支。
- **待验证**：作者连续一周自用。看两点：回来后 1 分钟内能否说出“先处理哪个、做什么”；「很久没动」能否清到 0。

## 5. 已知限制与后续

- 收件箱的数据范围是账本保留期（默认 30 天），更早的会话不会出现。“被遗忘的会话为 0”这一指标只在保留期内成立。
- 每次读取返回全部 469 行（1.4 MB），并且每 30 秒刷新一次。可以考虑只返回原话的首条和最近几条，或把「已结束」分页。
- 「已完成」要求会话有回合记录，没有回合的会话只能放弃。
- 结局写入后会发 `ledger:update` 事件；菜单栏计数暂未改为按收件箱分组。

## 6. 可能与主 checkout 未提交改动冲突的文件

主 checkout 有“轻量会话概览”这条线的未提交改动。本分支尽量用了新文件，两边都改过的只有：

| 文件 | 本分支改动 | 主 checkout 改动 | 预计 |
|---|---|---|---|
| `src/local-api/routes/meta.ts` | capabilities 增加 `inbox.outcomes` | `serviceVersion` 改读 package.json | 不同块，应能自动合并 |
| `src/web/client/tests/ui/workspace.spec.ts` | 6 处 `goto("/")` 改为 `?view=overview` | 新增和调整概览用例 | 同文件不同行；合并后要检查主线新增用例是否也依赖“默认首页 = 总览” |

行为上要注意：合并后默认首页变为收件箱，主线 `LedgerRecap`（概览抽屉）仍在「总览」下。两边都在展示“最近回复 / 执行与检查 / 文件变化”，但数据规则不同：`LedgerRecap` 显示全部执行记录，本分支的卡片只认检查命令和本会话产生的证据。建议合并后统一成一套“做成了”规则。
