# Keepline 产品卡

状态：方向已由用户认同，待验证；技术架构于 2026-10-20 按开源库测评定案（见第 3.1 节）。日期：2026-10-20。源码基线：`main@0d32d2b`。

本卡回答「Keepline 到底做什么、做成什么形态」，位于各 Spec 之上。实现细节以
[终端工作台 Spec](terminal-workbench/product.md) 与
[进度账本 Spec](progress-ledger/product.md) 为准；两者与本卡冲突处，见第 9 节。

## 1. 这张卡支撑的决定

- **决定**：Keepline 做「专门跑和管理 Agent 的桌面 App，每个会话是 App 内的一个真实终端」，
  而不是终端模拟器、聊天型客户端或某个第三方终端之上的插件。
- **衡量指标**：见第 7 节。
- **放弃条件**：见第 8 节。

## 2. 用户与问题

**目标用户**：同时开 10–40 个 Claude Code、Codex 会话的开发者，面向公开用户，不只是作者自用。

**核心问题**：会话一多，人记不住。一个会话离开视线就等于被遗忘；几小时后再找回来，
已不清楚它做到哪、该做什么。作者本机实测：Herdr 中 46 个 Agent 有 45 个显示 `idle`，
进程状态无法区分「做完待核对」「做一半停了」「早该关掉」。

**产品要守住的两件事**：

1. **不丢**：每个未了结的会话都被记住，直到用户明确给出结局。
2. **回得来**：回来后 1 分钟内知道先处理哪个、要做什么，并一步回到那个会话继续。

## 3. 定位与形态

一句话：**一个专门用来跑和管理 Agent 的 App，里面的每个会话都是一个真实的终端。**
用户日常命令行工作照旧在自己的终端里做，Agent 统一在 Keepline 中启动和继续。

| 方案 | 结论 | 原因 |
|---|---|---|
| 做终端模拟器（对标 Ghostty、Warp） | 否定 | 价值不在终端本身，且须承担通用终端的全部门槛 |
| 聊天型客户端（经 SDK / stream-json / app-server 驱动 CLI） | 否定（首版） | 需追两家协议与功能，直接撞上官方多会话产品 |
| 建在 Herdr、tmux 等第三方宿主之上 | 否定 | 依赖第三方变更，且要求用户先改用它 |
| 跑在终端里的 TUI | 备选 | 性能白拿，但收件箱、卡片、diff 在字符界面难做清楚，且与 Herdr 同质 |
| **App 内嵌真实终端（原生 CLI 跑在 App 的 PTY 中）** | **采用** | 功能完整度由原生 CLI 保证；所有会话在一个窗口；PTY 在手，可做可靠的「继续」 |

唯一不可避免的外部依赖是 Claude Code、Codex 本身：读取其会话记录、接收其 Hook、调用其
`resume`。这层是产品原料，不再叠加其他第三方。

## 3.1 技术架构与资源预算（2026-10-20 定案）

依据：终端技术栈开源库测评（分支 `claude/terminal-eval-04a203` 的 `eval/terminal/`，含原始数据、findings 与逐层决策记录）。阶段 2 按用户决定于 2026-10-20 终止，未测项列在下方。

```text
┌────────────── 常驻：一个 Rust 后台进程 ──────────────┐      ┌──── 界面：GPUI 客户端（Rust） ────┐
│ PTY 与进程管理（库做零件，循环自写）                  │      │ 空间 / 标签 / 分屏 / 鸟瞰 / 卡片    │
│ 终端状态：libghostty-vt（40 会话，含快照与空闲压缩）  │◀────▶│ 画面：GPUI 自绘 + libghostty-vt    │
│ 会话复用与重连协议：自写（kl-relay 演进）             │attach│ 窗口关闭即断开，后台不受影响        │
│ 会话记录、Hook、「你在这里」卡、结局状态、SQLite      │      └───────────────────────────────────┘
└──────────────────────────────────────────────────────┘
```

| 层 | 决定 | 主要依据 |
|---|---|---|
| 常驻进程 | 全部进一个 Rust 后台进程；Bun 服务不再常驻 | 现有 Bun 服务仅观察 73 个会话就常驻约 240 MB 数据并每 5 秒轮询；运行时本身只有约 22 MB，问题在数据常驻与轮询 |
| 终端状态（VT） | 采用 libghostty-vt | 40 会话 × 1 万行：405 MiB（alacritty 1.29 GiB，rio 427 MiB），空闲压缩后约 66 MiB；唯一有完整快照（首屏 0.09 ms）；esctest 147 项通过（另两家 101）；真实 Codex 录制解析最快 |
| 会话复用与重连 | 自写 | 无可嵌入的库；kl-relay 原型 40 会话空闲 35 MiB、CPU 0.13% |
| 界面框架与画面 | **GPUI**，画面用 libghostty-vt，前后台同一引擎；Swift + GhosttyKit 作备选 | 1 画面真实 Codex 287 MiB / 5.4–5.9%（Ghostty.app 316 MiB / 9.8%）；4 画面真实 Codex 327 MiB / 11–13%，内存低于 GhosttyKit 路线；用户选择全 Rust 路线 |
| WebView（Tauri + xterm.js） | 否定 | 同负载约为原生 3.5 倍内存，GPU 进程占用不可预测 |

**资源预算**：同机同负载相对 Ghostty ≤ 1.2 倍（物理内存 `phys_footprint`，覆盖全部子进程与系统辅助进程；累计 CPU 时间）。另有绝对要求：窗口隐藏时不渲染、CPU 接近 0；空闲时无轮询。

**已接受的风险与未测项**（用户决定不再测试，首个实现时必须验收）：

1. 中文输入法未测，仍是硬门槛。GPUI 在 Zed 中仍有中文输入法相关问题（zed#59882、#53537）。首个可用版本必须通过输入法清单；不过关时切换到备选 Swift + GhosttyKit。
2. GPUI 窗口可见时按刷新率持续唤醒，空闲 CPU 0.8%，约为 Ghostty 的 8 倍，不过线。需打补丁暂停显示链接（实测降到 0.07%），因此要长期维护 GPUI 补丁或分支；补丁的空闲阈值（0.5 s）尚未测。
3. gpui 发行线分裂，需锁定 Zed rev 或 gpui-kit 之一。
4. libghostty-vt 未正式发版：锁 commit，构建引入 Zig 工具链。
5. 未测：4 画面的 Ghostty 基准、GPU 与耗电、输入延迟；Claude Code 全屏重绘只有合成负载。

**切换到备选（Swift + GhosttyKit）的条件**：中文输入法不过关且短期修不好；或空闲补丁无法稳定维护；或 4 画面资源超出预算。

## 4. 主界面

两种视图，加上每个画面内的状态标注。设计稿见 [Keepline 工作台画布](https://claude.ai/artifact/D7QTQJmv6VZdPeqcKwHxoU)（私有链接）。

### 工作视图（日常）

```text
┌──────────────┬──────────────────────────────────────────────────────┐
│ 空间          │ [tes] [webs] [keepline] [codex- ●] [steal ●] …  标签  │
│ lib    ●2 14 ├───────────────────────────┬──────────────────────────┤
│ sys    ●1 11 │ 待核对 · 测试 42/42 · 未提交 │ 等你回答 · 批准 git push   │
│ …            │                           │      真实终端             │
│              │        真实终端            ├──────────────────────────┤
│ 需要你 · 5    │                           │ 进行中 · 运行 4 分钟       │
│ ● 反馈接口    │                           │      真实终端             │
│ ● SSH 异常    │                           │                          │
│ 鸟瞰全部 →    │                           │                          │
└──────────────┴───────────────────────────┴──────────────────────────┘
```

- 结构沿用多会话用户已有的习惯（以作者的 Herdr 用法为参照）：左边是空间，顶部是标签，每个标签分成 2–4 个画面同时可见。
- 每个画面顶部有一条状态栏：分组颜色、一句「你在这里」摘要、Agent / 项目 / 时间。点「你在这里」按需弹出完整卡片，卡片不常驻占一栏。
- 标签和空间上显示需要你的角标（等你回答、出错了）。
- 左栏只放空间列表和「需要你」短列表（等你回答与出错了，单行显示，通常 3–8 个）；全部会话在鸟瞰视图里查看，左栏不承担完整列表。
- 只渲染当前标签里可见的画面（最多 4 个）；其他会话在后台继续解析输出，不绘制。

### 鸟瞰视图（回来时）

- 离开超过设定时长后打开 App，默认先显示鸟瞰视图；任何时候点顶栏的「鸟瞰」按钮切换。每个功能都有看得见的按钮，首版先不做快捷键；以后加快捷键也只作为按钮的补充。
- 所有未闭环会话缩成小卡片铺满一屏，按 等你回答 / 出错了 / 待核对 / 做一半停了 / 进行中 分区。每张卡只有标题、空间与 Agent、一句状态；离开后有变化的标「新」。40 张卡一屏放得下。
- 「很久没动」「暂存」「已结束」折叠成计数，「很久没动」进入逐个清理。
- 点卡片回到它所在的标签和画面并聚焦；不在任何画面里的会话，在当前空间新开标签打开。
- 可按空间筛选，可只看有变化的会话。

### 菜单栏

只显示「几个在等你」和通知，点击直达对应画面。

## 5. 核心对象

### 「你在这里」卡（每个会话一张）

| 字段 | 来源 | 规则 |
|---|---|---|
| 你要它做什么 | 用户原话（含追加要求） | 原文，不改写 |
| 做成了什么 | 退出码、测试结果、文件改动、提交 | 只认机械证据，Agent 自述不算 |
| 停在哪 | 最后一轮的工具调用、错误、待回答问题 | 机械提取优先 |
| 下一步 | 由上三项推导，可选模型摘要 | 标明是推断；不编造证据 |

### 结局状态

每个会话必须有结局；没有结局的都算「未闭环」，一直留在鸟瞰视图里。

| 状态 | 含义 | 谁来设 |
|---|---|---|
| 进行中 / 等你 / 出错 / 待核对 | 未闭环，由事实推导 | 系统 |
| 已完成 | 用户核对并验收 | 仅用户 |
| 暂存 | 写明原因与再看时间，到期重新浮出 | 用户 |
| 已放弃 | 不再处理 | 用户 |

超过设定天数没有变化、又没有结局的会话进入「很久没动」，提供逐个清理入口。

### 待办与对象关系

待办是一件要交给 Agent 做的事，属于一个空间，带说明与可选的验收标准，可以对应多个会话。对象分两套关系：「做什么」是空间 → 待办 → 会话；「放在哪」是空间 → 标签 → 画面 → 终端；两者只在「会话跑在某个终端里」相连。**会话算哪件事看它挂在哪条待办上，显示在哪看它在哪个画面里，两者互不推导。** 默认行为让多数时候一个标签就是一条待办：点待办「开始」新建待办的标签，再开会话就在这个标签里分屏；关掉标签只收起视图，不停会话。完整规则见 [终端工作台 Spec 4.3](terminal-workbench/product.md#43-对象关系做什么与放在哪)。

### 新建

不做「新建 Agent」表单。新建只有一个机制：**开一个新画面，可选地预填一条命令，用户按回车才执行。** 入口是标签行「＋」与分屏（空 shell）、待办的「开始」（预填带待办说明与验收标准的 `codex` / `claude` 命令）、已退出会话的「继续」（预填 resume 命令）。第一次打开 App 直接给一个能输入的终端。

## 6. 「继续」怎么工作

所有继续都发生在 App 内，**不打开 Ghostty 或其他外部终端**。

| 情况 | 行为 |
|---|---|
| 托管会话、进程在跑 | 切到它所在的标签和画面，聚焦可输入 |
| 托管会话、进程已退出 | 在 App 内新开画面（放在它所属待办的标签里，没有则新标签），预填原 CLI 的 `resume` 命令，用户按回车后与原记录建立续接关系；也可「复制命令」 |
| 外部会话（在其他终端启动）、已退出 | 同上，预填 `resume`，用户按回车后成为托管会话 |
| 外部会话、仍在运行 | 不接管，不重复 resume；说明它在哪个终端，提示用户在原处处理或先结束原进程 |
| 同一会话重复点击 | 永远只有一个画面、一个执行者 |

`resume` 可附带由「你在这里」卡生成的续接提示（两个 CLI 均支持「会话 ID + 初始提示」）。
提示须先展示给用户，不自动发送。

## 7. 首版范围与指标

### 首版做

1. 鸟瞰视图与结局状态（含暂存到期、很久没动与逐个清理）。
2. 每轮自动更新的「你在这里」卡，以及画面状态栏上的一句摘要。
3. 分屏工作视图：空间、标签、每个标签 2–4 个画面，标签与空间的需要你角标，精简左栏。
4. App 内的终端画面：用户自己启动 Claude Code、Codex 等，原生 CLI 跑在真实 PTY 中；识别 Agent 后挂上状态栏与卡片。
5. 待办：新建、从待办开始（预填命令）、待办的标签与信息条、待办详情（验收标准与关联会话）。
6. 第 6 节的「继续」规则，含外部会话的 App 内 resume。
7. 菜单栏计数与通知直达。

### 首版不做

终端模拟器的通用功能（SSH、自由拖拽的任意分屏布局、广播输入；首版分屏限于每个标签 2–4 个画面的规则网格）、自建聊天界面、在列表里一键批准
（与终端工作台 Spec 6.3 一致，作为后续候选）、成本分析与主题、跨会话记忆、云同步、
Windows/Linux。

### 衡量指标

| 指标 | 目标 |
|---|---|
| 回来后说出「先处理哪个、做什么」 | 离开 30 分钟以上，1 分钟内 |
| 被遗忘的会话 | 超过设定天数既无变化又无结局的为 0（都已在「很久没动」中被处理） |
| 回到旧会话后说清进度 | 30 秒内，不需翻原始记录 |
| 决定后到能在会话里打字 | 5 秒内 |
| 终端体验 | 同时 40 个会话，同一标签 4 个终端同时可见并持续输出；切换 100ms 内出画面；输入延迟与 Ghostty 无可感知差异；中文输入法正确 |
| 资源 | 同机同负载相对 Ghostty ≤ 1.2 倍（phys_footprint 与累计 CPU，覆盖全部进程）；窗口隐藏时 CPU 接近 0 |

## 8. 放弃条件

- GPUI 路线在中文输入法、空闲功耗或 4 画面资源上不过关且短期修不好：切换到备选 Swift + GhosttyKit；
  备选也不过关时，停止「App 内终端」路线，重新评估 TUI 备选。
- 资源超出预算时先定位层：界面层超出就换界面技术；后台层超出就优化后台，不以更换界面替代。
- 「你在这里」卡经常不准，用户仍需翻记录：停止往上加界面，先回头解决数据来源。
- 作者本人连续一周使用后，回来定位下一步并不比翻终端标签更快，或仍有会话被遗忘：方向不成立，重新定义问题。

| 会话扫描、进程匹配、Hook、证据提取、恢复命令 | 保留，是鸟瞰视图与卡片的数据来源 |
| 进度账本（要求条目、证据、验收） | 保留核心；首屏只用轻量接手信息，完整账本降为二级入口 |

| Bun 业务服务（`src/`） | 不再常驻；会话记录读取、Hook、卡片与结局状态迁入 Rust 后台。现有 TS 代码作为迁移参照，CLI 等非常驻用途可暂留 |
| Tauri 前端与 React 页面 | 不作为新 App 的界面；主界面改为 GPUI。现有页面在迁移完成前继续服务观察用途 |

| 菜单栏 App（1.2.0 候选） | 是否先发布由用户决定；新架构下菜单栏由 GPUI 客户端或轻量原生组件承担，收窄为计数与直达 |
