# 本机 CPU / GPU 诊断功能分析

2026-10-28 可行性分析；2026-10-29 已实现按需版本，具体交付与验证见末节。范围为当前 `next/` 原生 Keepline。

## 支撑的决定

决定是否在 Keepline 中加入一个入口，回答“这台 Mac 现在是什么在占 CPU / GPU”，并将采样证据交给用户已有的 Agent 继续分析原因。

**决定：采用按需诊断；CPU 排行可做，GPU 先提供本机可读范围内的数据，自动解释原因仍需额外证据。**

最小版的效果应是：用户点击“诊断本机”，后台采样 10～15 秒，显示整机负载、按应用归组的 CPU 排行、GPU 活动排行和采样时间，并能复制诊断摘要给 Agent。采样结束或关闭视图后停止。不默认常驻采样、不改节点、不结束进程。

## 当前代码能复用什么

- `next/crates/keeplined/src/recognition.rs:214`：已有托管 PTY 子进程枚举与进程关系识别，当前明确不扫描全机。因此不能直接把它扩成全机定时扫描，否则会改变会话识别边界。
- `next/crates/keepline-core/src/model.rs:137`：Terminal 保存 PID，可用来指出采样进程是否属于某个 Keepline 终端。共享 app-server 或无法证明的进程归属保持未关联，不能按目录或名字硬分摊到会话。
- `next/crates/keepline-core/src/protocol.rs:25`、`next/crates/keepline-app/src/connection.rs:202`：已有类型化 Unix socket 协议、状态订阅及断开释放，可沿用通信方式。
- `next/crates/keepline-app/src/workbench/render.rs:4`：原生界面已有顶栏和主区视图切换，可以接入一个诊断入口与结果视图。

本轮检索没有发现 `next/crates/` 已有全机 CPU/GPU 采样或通用 LLM 诊断服务。不能把“已有终端和 Agent”当成“已有自动诊断能力”。

## 数据与权限实测

本次在用户当前 M3 Max / 128GB Mac 上检查，不代表其他 macOS 或机型已通过。

| 能力 | 实测及边界 |
|---|---|
| CPU 按进程排行 | 前序诊断已用普通用户执行 `ps` 读取 Clash 等进程的累计 CPU 时间，跨采样间隔计算占用。首版可采用一轮批量读取，避免逐 PID 启动命令。 |
| 直接读取任务统计 | `libproc` 的 `PROC_PIDTASKINFO` 对采样进程自身返回完整结构；对 Clash PID 35431、WindowServer PID 397 返回 EPERM。不能假设原生 API 对全机进程都可读。 |
| 整机 GPU 活跃度 | `ioreg -a -r -l -c AGXAccelerator` 可读本机 `PerformanceStatistics` 的设备活跃度。它是驱动提供的统计字段，尚未验证跨系统和机型稳定性。 |
| GPU 按进程活动 | 同次读取看到 122 个 GPU 客户端，其中 40 个有非空 AppUsage。前序诊断已观察到累计 GPU 时间随进程变化，可用于活动排序。无数据不等于 GPU 占用为零；同一进程的多个客户端需要合并。 |
| 深入函数热点 | `sample` 无权读取当前特权 Clash 进程；其 pprof HTTP 入口返回 404。基础功能不依赖这一能力。 |
| GPU 功耗及更深统计 | 前序 `sudo -n powermetrics` 提示需要密码。本轮不将其作为必需数据源。 |

Apple 的 [proc_taskinfo 源码定义](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h)提供累计 CPU 时间、RSS 等字段；可调用接口不代表本机对所有目标 PID 都授予读取权限。

[IORegistryEntryCreateCFProperties](https://developer.apple.com/documentation/iokit/1514310-ioregistryentrycreatecfpropertie)是读取 registry 属性快照的公共接口；这不能证明上述 GPU 驱动属性具备同等稳定契约。GPU 时间增量在已观测进程间的占比，也不是整颗 GPU 的利用率，更不应乘以设备活跃度来分配百分比。

## 最小接入方式

1. 在现有 Rust 后台增加一个具体采样模块；通过现有 socket 提供有界诊断请求与结果，采集工作在业务状态锁外进行。
2. 采样结果保留时间、间隔、CPU 口径和缺失数据说明；使用相同进程身份的累计时间差，防止 PID 重用造成错误增量。整机 CPU 按 0～100% 表示；进程 CPU 的 100% 表示占用一个核心。
3. 不把采样结果写进 Workspace、业务 SQLite 或会话结局。结果只服务当前诊断视图；界面只刷新诊断区域，不因采样刷新所有终端。
4. 界面显示应用 CPU 排行与可读 GPU 活动；能证明属于托管终端的进程附上终端入口。首版提供“复制诊断摘要”，交给用户已有的 Agent 分析。

所需新增代码范围预计是一个采样模块与一个诊断视图，并修改现有协议、后台分发及界面入口；不增加独立服务、配置层、插件框架或新数据库。

## “为什么占用高”能做到什么程度

CPU/GPU 数字足以回答“谁在用”，不能单独证明“为什么”。例如本次 Clash 诊断中，微信占下载流量约 98%、相关连接经过 TUN，是额外读取 Clash 本地 API 得到的证据；后续 CPU 和下载同时下降只是支持流量负载假设，尚未经过暂停下载等干预验证。

因此首版应把真实采样及未知项交给 Agent。需要进一步读日志、请求本机服务 API 或获取调用栈时，再按当次问题取证。不要为这个案例添加“Clash 高 CPU 就是微信下载”等硬编码诊断规则，也不要默认扫描其他应用日志、令牌或连接配置。

## 采样成本与验收、放弃条件

本机三次短探测，单次全进程 `ps` 耗时约 74～78ms，子进程 CPU 时间约 72～75ms；GPU registry 读取约 26～28ms、CPU 时间约 24～25ms。输出分别约 230KB 与 206KB。它们只是当前机器的命令开销，不是最终 Rust 实现性能结论。

由此估算，每秒各执行一次，两项子进程本身就可能消耗约 10% 单核心 CPU，尚不包含解析及绘制。首版建议每 5 秒取一轮、持续 10～15 秒，结束即停止；不要直接变成常驻秒刷仪表盘。

- 验收：同一时窗与系统工具比较累计 CPU 增量；检查短命进程、应用多进程、托管 Agent 子进程、缺失 GPU 数据和无权限进程。
- 验收：关闭诊断后无后续采样；不影响输入、终端输出或会话识别。额外 CPU 预算暂定平均不超过单核心 3%，需在集成后实测，不能由命令探测代替。
- 若基础排行必须常驻提权，放弃该路径，保留可读数据并明确缺项。
- 若 GPU 字段在目标机器不可读，或成本超预算，首版缩为 CPU 与整机概况，不伪造 GPU 数字。
- 若用户希望无操作就能解释所有应用的根因，该目标目前证据不足；不以堆规则或开启全量日志扫描补足。

## 本轮收尾

已验：当前源码的进程识别范围、协议和 UI 接入位置；普通用户权限差异；本机 GPU 字段覆盖；采集命令的三次成本探测。

没验：Keepline 集成后的功耗、输入流畅度和结果准确度；本轮未编写业务代码或做原生 UI 交互验收。

相邻情况：特权 Clash 与 WindowServer 的任务信息权限已测；Intel Mac、其他 Apple Silicon、其他 macOS 版本以及共享 Agent 后台的精确会话归因未测。


## 2026-10-29 实现与验证

决定：采用现有 Rust 后台中的按需采样与独立诊断视图。实现已落在 `next/`，没有新增服务、配置项或数据库表。

左侧栏底部固定的“本机诊断”打开面板，采样两段 7.5 秒区间，约 15 秒结束；关闭、Esc 或“停止采样”断开采样连接。显示整机 CPU 平均、GPU 最新设备活跃度、按应用合并的 CPU 平均与区间峰值、RSS、GPU 已观测活动份额，并提供可确认归属的终端入口及复制摘要。复制不调用远程模型，也不自动发送给 Agent。

实现位置：

- `next/crates/keepline-core/src/diagnostics.rs` 定义临时测量结果与摘要；协议新增 `Diagnose` / `Diagnostics`。
- `next/crates/keeplined/src/diagnostics.rs` 批量读取系统工具、计算时间差、应用归组和终端进程树归属；单次采样任务在工作区锁外运行。
- `next/crates/keepline-app/src/workbench/diagnostics.rs` 独立 GPUI Entity 接收有限结果，关闭时释放 socket，不触发整个 Workspace 同步。

采样窗口从最初约 10 秒调整为约 15 秒。一次本机后台测量（包含其 ps/ioreg 子进程）在 15.4 秒期间消耗约单核心 2.72% CPU；结束后观察 5 秒，后台和子进程累计 CPU 时间均无变化。此处按本机 Mach timebase 125/3 换算 CPU 计数，没有把原始计数当作纳秒。该数字只代表本次后台采样，不是所有机型的保证，也没有覆盖前端长期功耗。

已验：真实忙碌托管 shell 出现在 CPU 排行并关联到终端；采样期间工作区请求继续返回且 revision 不变；GPU 计数解析及缺失情况；PID 重用不沿用旧终端归属；取消唤醒等待并回收自建采样子进程。原生渲染已看到真实排行，复制摘要已读回核对；Esc 关闭取消、重新打开采样及从结果回到对应终端的原生事件路径已验证。

没验：其他机型/系统版本、长时间功耗、打包应用的跨机器分发与公证。相邻情况：共享后台保持未关联；诊断不自动读取 Clash API、改节点或结束业务进程。

本地预览包与截图、实际报告和资源测量记录保存在 `next/target/diagnostics-preview/`。本轮没有提交、推送或发布，正在使用的旧应用实例未替换。


### 2026-10-29 入口位置调整

按用户确认，将“本机诊断”从顶栏移到左下角固定工具区。侧栏的空间、会话与待办列表单独滚动；诊断按钮放在该滚动容器之外，不随列表滚走。采用现有面板与采样逻辑，未增加新页面或后台采样任务。

已验：原生界面中的左下角入口可点击打开诊断；30 个布局测试空间的长列表情况下按钮仍固定可见；诊断采样、复制及终端跳转复验通过。没验：更窄窗口下的布局。相邻情况：短列表与长列表均已验。本地预览包已更新，运行中的旧应用实例未替换。
